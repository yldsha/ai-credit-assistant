# Тестовые сценарии кредитного кабинета

**Проект:** «Умный кредитный кабинет предпринимателя»  
**Цель:** проверка работы кредитного конвейера, корректности кредитных решений, переходов между статусами и обработки нестандартных ситуаций.

## 1. Общая информация

Для функционального тестирования используются десять сценариев с синтетическими данными предпринимателей и организаций.

Первые пять сценариев проверяют основные результаты кредитного процесса:

1. Автоматическое одобрение.
2. Передачу заявки на ручное рассмотрение.
3. Автоматический отказ.
4. Ручное рассмотрение заявки с крупной суммой.
5. Запрос недостающей информации.

Дополнительно предусмотрены два сценария, проверяющие обработку критических ограничений и отказоустойчивость системы, и три сценария (8–10), в которых вероятность дефолта рассчитывает модель CatBoost в реальном времени.

Тестовые компании и ответы внешних источников заданы в `mocks/data/seed.json`.

Правила кредитной политики определяются в `scoring/decision/config.json`.

Основные параметры:

| Параметр | Значение |
|---|---|
| Максимальная PD для автоматического одобрения | 5% |
| PD для автоматического отказа | От 15% включительно |
| Порог обязательного ручного рассмотрения | Свыше 3 000 000 ₽ |
| Максимальная допустимая платёжная нагрузка | 50% |
| Критическая просрочка | Более 90 дней |
| Дополнительный риск по просрочке | Более 30 дней |
| Повышенное количество запросов в БКИ | Более 5 за 6 месяцев |

## 3. Подробное описание тестовых сценариев

### Сценарий № 1. Автоматическое одобрение

**Цель:** проверить, что заявка клиента с низкой вероятностью дефолта, допустимой суммой кредита и отсутствием дополнительных факторов риска обрабатывается автоматически.

**Данные клиента:**

| Параметр | Значение |
|---|---|
| Клиент | ИП Петров Иван Сергеевич |
| ИНН | 770200000001 |
| Регион | Москва |
| Сфера деятельности | Торговля |
| Сумма кредита | 1 000 000 ₽ |
| Срок | 24 месяца |
| Цель | Закупка товаров |
| Годовая выручка | 24 000 000 ₽ |
| Действующие ежемесячные кредитные платежи | 50 000 ₽ |
| PD | 2% |

**Предусловия:**

- Компания имеет действующий статус.
- Не выявлены критические ограничения.
- Отсутствуют просрочки и дополнительные признаки риска.
- Получено согласие на запрос кредитной истории.

**Последовательность действий:**

1. Клиент открывает кредитный кабинет.
2. Выбирает параметры финансирования.
3. Заполняет данные заявки.
4. Отправляет заявку на рассмотрение.
5. Система получает информацию из внешних источников.
6. Рассчитывается вероятность дефолта.
7. Decision Engine применяет кредитные правила.
8. Клиент получает решение.

**Ожидаемый результат:** `approved`.

Заявка должна быть одобрена без участия сотрудника.

**Ожидаемая история статусов:**

`draft → submitted → checking → scoring → approved`

**Дополнительные проверки:**

- PD соответствует демонстрационному значению 2%.
- Сумма не превышает порог автоматического одобрения.
- Платёжная нагрузка составляет около 7% (для продукта, выбранного подбором).
- Клиенту отображаются условия предложения.
- В истории сохраняется изменение статуса.

**Критерий успешности:** итоговый статус `approved`, корректно рассчитанные условия и сохранённая история обработки.

### Сценарий № 2. Ручное рассмотрение из-за уровня риска

**Цель:** проверить маршрутизацию заявки с пограничной вероятностью дефолта к сотруднику банка.

**Данные клиента:**

| Параметр | Значение |
|---|---|
| Клиент | ООО «Вектор» |
| ИНН | 7702000002 |
| Регион | Санкт-Петербург |
| Сфера деятельности | Производство |
| Сумма кредита | 2 000 000 ₽ |
| Срок | 36 месяцев |
| Цель | Приобретение оборудования |
| Годовая выручка | 36 000 000 ₽ |
| Ежемесячные платежи | 80 000 ₽ |
| PD | 9% |

**Предусловия:**

- Компания действующая.
- Критических стоп-факторов нет.
- Данные для расчёта риска доступны.

**Последовательность действий:**

1. Клиент формирует кредитную заявку.
2. Система проверяет сведения о компании.
3. Выполняется скоринговая оценка.
4. Decision Engine определяет PD 9%.
5. Система фиксирует превышение порога автоматического одобрения.
6. Заявка передаётся сотруднику.

**Ожидаемый результат:** `manual_review`.

**Ожидаемая история статусов:**

`draft → submitted → checking → scoring → manual_review`

**Что должен увидеть сотрудник:**

- PD 9%.
- Указание на пограничную зону риска.
- Факторы, повлиявшие на оценку.
- Рекомендацию системы по дальнейшему рассмотрению.

**Критерий успешности:** система не принимает автоматическое одобрение или отказ, а направляет заявку на ручную проверку.

### Сценарий № 3. Автоматический отказ по высокому риску

**Цель:** проверить отказ при превышении порога вероятности дефолта.

**Данные клиента:**

| Параметр | Значение |
|---|---|
| Клиент | ИП Смирнов Алексей Петрович |
| ИНН | 770200000003 |
| Регион | Казань |
| Сфера деятельности | Общественное питание |
| Сумма кредита | 1 500 000 ₽ |
| Срок | 24 месяца |
| Цель | Развитие бизнеса |
| Годовая выручка | 18 000 000 ₽ |
| Ежемесячные платежи | 60 000 ₽ |
| PD | 23% |
| Максимальная просрочка за год | 45 дней |
| Запросы в БКИ за 6 месяцев | 6 |

**Последовательность действий:**

1. Клиент отправляет кредитную заявку.
2. Система получает данные из внешних источников.
3. Выполняется скоринговая оценка.
4. Decision Engine получает PD 23%.
5. Система сопоставляет результат с порогом отказа 15%.
6. Формируется отрицательное решение.

**Ожидаемый результат:** `rejected`.

**Ожидаемая история статусов:**

`draft → submitted → checking → scoring → rejected`

**Причины для внутреннего анализа:**

- PD превышает допустимый порог.
- Просрочки в кредитной истории.
- Повышенное количество кредитных запросов.
- Факторы риска, сформированные для демонстрационного клиента.

Просрочка 45 дней является дополнительным фактором риска, но не достигает критического порога более 90 дней.

**Критерий успешности:** система формирует отказ на основании высокого PD, сохраняет решение и отображает клиенту предусмотренное объяснение.

### Сценарий № 4. Ручное рассмотрение крупной заявки

**Цель:** проверить применение лимита суммы кредитного предложения.

**Данные клиента:**

| Параметр | Значение |
|---|---|
| Клиент | ООО «Прогресс» |
| ИНН | 7702000004 |
| Регион | Екатеринбург |
| Сфера деятельности | Оптовая торговля |
| Сумма кредита | 5 000 000 ₽ |
| Срок | 36 месяцев |
| Цель | Пополнение оборотных средств |
| Годовая выручка | 120 000 000 ₽ |
| Ежемесячные платежи | 100 000 ₽ |
| PD | 3% |

**Предусловия:**

- Компания действующая.
- Критические стоп-факторы отсутствуют.
- Платёжная нагрузка соответствует допустимому ограничению.

**Последовательность действий:**

1. Клиент оформляет заявку на 5 млн рублей.
2. Система выполняет проверки.
3. Рассчитывается PD 3%.
4. Decision Engine проверяет платёжную нагрузку.
5. Сумма предложения сопоставляется с лимитом 3 млн рублей.
6. Заявка направляется сотруднику.

**Ожидаемый результат:** `manual_review`.

**Ожидаемая история статусов:**

`draft → submitted → checking → scoring → manual_review`

**Обоснование результата:**

Несмотря на низкую вероятность дефолта, рассчитанная сумма предложения превышает установленный лимит автоматического решения.

Важно: в текущем Decision Engine порог сравнивается с суммой после возможной корректировки по платёжной нагрузке. В данном сценарии предполагается, что сумма остаётся 5 млн рублей.

**Критерий успешности:** система направляет заявку сотруднику с указанием причины — превышения лимита автоматического рассмотрения.

### Сценарий № 5. Запрос недостающей информации

**Цель:** проверить обработку заявки с отсутствующим обязательным финансовым показателем.

**Данные клиента:**

| Параметр | Значение |
|---|---|
| Клиент | ООО «Меридиан» |
| ИНН | 7702000005 |
| Регион | Новосибирск |
| Сфера деятельности | Информационные технологии |
| Сумма кредита | 800 000 ₽ |
| Срок | 12 месяцев |
| Цель | Приобретение оборудования |
| Годовая выручка | Не указана |

**Последовательность действий:**

1. Клиент создаёт кредитную заявку.
2. Поле `annual_revenue` передаётся со значением `null`.
3. Заявка отправляется на рассмотрение.
4. Система запускает предусмотренные проверки.
5. Decision Engine выявляет отсутствие обязательной информации.
6. Формируется запрос на дополнение данных.

**Ожидаемый результат:** `need_info`.

**Ожидаемая история статусов:**

`draft → submitted → checking → scoring → need_info`

**Что должен увидеть клиент:**

- Статус «Нужна информация».
- Сообщение о недостаточности данных.
- Указание на необходимость предоставить годовую выручку.

**Важная особенность проверки:**

Входной параметр необходимо передать явно:

`"annual_revenue": null`

Если просто исключить поле из JSON-запроса, может быть использовано значение по умолчанию, заданное в модели данных API.

Отсутствие выручки обрабатывается как `need_info` (подтверждено прогоном). Клиент может дополнить данные через `POST /applications/{id}/supplement` и повторно отправить заявку.

**Критерий успешности:** получение статуса `need_info` с указанием отсутствующего показателя и возможностью повторной отправки заявки после дополнения.

### Сценарий № 6. Отказ по критическому стоп-фактору

**Цель:** проверить применение обязательного ограничения при нахождении организации в процессе ликвидации.

**Данные клиента:**

| Параметр | Значение |
|---|---|

| ИНН | 7702000006 |
| Регион | Самара |
| Сфера деятельности | Торговля |
| Сумма кредита | 1 000 000 ₽ |
| Срок | 24 месяца |
| Годовая выручка | 24 000 000 ₽ |
| Статус организации | Ликвидация |

**Последовательность действий:**

1. Клиент отправляет заявку.
2. Система получает сведения из внешних источников.
3. Выполняется предусмотренный этап скоринга.
4. Decision Engine проверяет критические ограничения.
5. Выявляется нахождение компании в процессе ликвидации.
6. Формируется отказ.

**Ожидаемый результат:** `rejected`.

**Особенность сценария:**

При этом в текущей реализации backend этап скоринга запускается до применения стоп-факторов в Decision Engine.

**Критерий успешности:** формирование отказа с фиксацией критического основания в данных решения.

### Сценарии № 8–10. Оценка риска моделью в реальном времени

**Цель:** проверить, что для клиентов без зафиксированного демо-значения PD вероятность дефолта и факторы риска рассчитывает модель CatBoost, а движок принимает решение на основе её результата.

Данные клиентов взяты из датасета модели (округлены). Значение PD не фиксируется — его считает модель.

| № | Клиент | ИНН | Заявка | Выручка / оборот / расходы в месяц / платежи по долгам в месяц | PD модели | Ожидаемый результат |
|---|---|---|---|---|---|---|
| 8 | ИП Соколова А. В., торговля | 770200000008 | 1 300 000 ₽, 12 мес., закупка товаров | 29 000 000 / 2 160 000 / 1 900 000 / 112 000 ₽ | ≈ 2,4% | `approved` |
| 9 | ООО «Литейщик», производство | 7702000009 | 1 200 000 ₽, 48 мес., рефинансирование | 24 250 000 / 1 875 000 / 1 146 000 / 793 500 ₽ | ≈ 9,5% | `manual_review` |
| 10 | ООО «Чистый дом», услуги | 7702000010 | 930 000 ₽, 48 мес., рефинансирование | 11 350 000 / 958 000 / 837 700 / 462 800 ₽ | ≈ 20,7% | `rejected` |

**Ожидаемая история статусов:** `draft → submitted → checking → scoring → <итоговый статус>`

**Дополнительные проверки:**

- `model_version` = `catboost-risk-v1` (а не демо-значение).
- `risk_factors` содержит пять факторов SHAP с направлением влияния.
- Для сценариев 9 и 10 главный фактор риска — «Долговая нагрузка».

**Критерий успешности:** PD рассчитан моделью, итоговый статус совпадает с ожидаемым, факторы риска сохранены.

Возраст бизнеса рассчитывается от даты регистрации до текущей даты, поэтому со временем PD может незначительно смещаться.

## 4. Инструкция по тестированию через Swagger

Тестовые сценарии можно проверить через API backend.

### 4.1. Запуск приложения

Из корневой папки проекта выполнить:

```bash
docker compose up --build
```

После запуска открыть:

`http://localhost:8000/docs`

### 4.2. Создание заявки

В Swagger выбрать:

`POST /applications/draft`

Нажать **Try it out** и вставить JSON соответствующего сценария.

После выполнения сохранить идентификатор созданной заявки из поля `application.id`.

### 4.3. Отправка заявки

Выбрать:

`POST /applications/{application_id}/submit`

Указать полученный ID и выполнить запрос.

### 4.4. Проверка результата

После завершения фоновой обработки выполнить запрос:

`GET /employee/applications/{application_id}`

Проверить:

- `status` — итоговый статус.
- `pd` — вероятность дефолта, если она рассчитана.
- `model_version` — кто рассчитал PD: `catboost-risk-v1` (модель) или `demo-seed-v1` (демо-значение).
- `decision_result` — результат применения кредитных правил.
- `employee_reasons` — внутреннее объяснение решения.
- `status_history` — историю состояний.

При необходимости повторить запрос, если фоновая обработка ещё не завершена.

## 7. Выводы

Разработанные тестовые сценарии охватывают основные ветки кредитного процесса: автоматическое одобрение, ручное рассмотрение, отказ, запрос дополнительных данных, применение критических ограничений, обработку недоступности внешнего сервиса и оценку риска моделью в реальном времени.

Тестирование направлено на проверку не только результата скоринга, но и взаимодействия компонентов кредитного конвейера.

Особое внимание уделяется корректности маршрутизации заявок, последовательности статусов и сохранению причин принятого решения.

Все десять сценариев пройдены: система корректно маршрутизирует заявки, сохраняет историю статусов и причины решений, а модель риска рассчитывает PD и факторы для новых клиентов.

Все использованные клиентские данные являются синтетическими и предназначены исключительно для демонстрации и тестирования проекта.
