# Продуктовая аналитика
## Умный кредитный кабинет предпринимателя
 
**Целевая аудитория:** малый и микробизнес  
**Цель документа:** обоснование потребностей пользователей, состава MVP, кредитных правил и продуктовых метрик.

---

## 1. Цель продукта

«Умный кредитный кабинет предпринимателя» — цифровой сервис, объединяющий выбор финансирования, оформление кредитной заявки, проверку данных, оценку кредитного риска и получение ответа в одном интерфейсе.

Основная задача продукта - сделать процесс кредитования более понятным и удобным для предпринимателя, одновременно сокращая количество операций, требующих участия сотрудника банка.

Продукт ориентирован на решение трёх основных задач:

- Упрощение подачи кредитной заявки.
- Автоматизация обработки стандартных обращений.
- Повышение прозрачности кредитного процесса.

## 2. Исследование пользователей и их потребностей

### 2.1. Целевая аудитория

Целевыми пользователями являются предприниматели и представители малого и микробизнеса, которые заинтересованы в получении финансирования.

Пользователи отличаются уровнем финансовой грамотности, опытом кредитования, масштабом бизнеса и целями финансирования, поэтому интерфейс должен быть понятным даже человеку, который ранее не оформлял кредит для бизнеса.

### 2.2. Потребности и задачи пользователей (Jobs To Be Done)

Основная потребность предпринимателя при оформлении кредита — получение финансирования на подходящих условиях с минимальными затратами времени и усилий. 

В рамках кредитного процесса можно выделить следующие задачи пользователя:

1. **Выбор финансирования:** определить, какой кредитный продукт лучше соответствует целям бизнеса(пополнению оборотных средств, приобретению оборудования или развитию компании).
2. **Определение параметров кредита:** выбрать необходимую сумму, срок кредитования и оценить предполагаемую финансовую нагрузку.
3. **Оформление заявки:** предоставить сведения о компании и её финансовом состоянии без необходимости многократного ввода одинаковой информации.
4. **Отслеживание рассмотрения:** получать актуальные сведения о статусе заявки и понимать на каком этапе находится проверка.
5. **Взаимодействие с банком:** при необходимости предоставлять дополнительные сведения и получать уведомления в личном кабинете.
6. **Получение результата:** ознакомиться с кредитным решением, предложенными условиями финансирования и дальнейшими действиями.

### 2.3. Основные боли клиентов

| Проблема | Последствия для клиента | Предлагаемое решение |
|---|---|---|
| Сложно выбрать кредитный продукт | Риск выбрать неподходящие условия | Подбор по цели финансирования |
| Много полей в анкете | Увеличение времени оформления | Автозаполнение доступных сведений |
| Непрозрачность рассмотрения | Неопределённость и дополнительные обращения | Отображение статусов заявки |
| Неизвестно время получения решения | Сложнее планировать расходы бизнеса | Информирование об этапе и сроке |
| Разрозненные каналы взаимодействия | Потеря контекста и дополнительные действия | Единый личный кабинет |


### 2.4. Сравнение клиентских путей

| Этап | Типичный процесс оформления | Предлагаемый кредитный кабинет |
|---|---|---|
| Выбор финансирования | Самостоятельное изучение предложений | Подбор по параметрам бизнеса |
| Заполнение данных | Ручное внесение сведений | Частичное автоматическое заполнение |
| Проверка информации | Клиент не всегда видит внутренние этапы | Прозрачная история статусов |
| Дополнительные сведения | Возможны отдельные каналы связи | Запрос внутри кабинета |
| Получение решения | Необходимость следовать инструкциям банка | Решение отображается в интерфейсе |

Сравнение отражает концептуальную модель пользовательского пути и не является измеренным сравнительным исследованием банковских сервисов.

### 2.5. Продуктовая ценность

**Для предпринимателя:**
- Сокращение ручного ввода информации.
- Более простой выбор кредитного продукта.
- Возможность отслеживать рассмотрение заявки.
- Получение решений и уведомлений внутри продукта.

**Для банка:**
- Автоматизация стандартных кредитных обращений.
- Снижение нагрузки на сотрудников.
- Повышение структурированности данных.
- Возможность контролировать процесс рассмотрения.

## 3. Определение объёма MVP

### 3.1. Цель MVP

MVP предназначен для демонстрации единого кредитного конвейера, объединяющего пользовательский интерфейс, проверку данных, скоринговую модель и принятие кредитного решения.

Основной приоритет — работоспособность сквозного сценария от подачи заявки до результата.

### 3.2. Приоритизация по MoSCoW

| Приоритет | Функциональность | Обоснование |
|---|---|---|
| Must have | Выбор кредитного продукта | Начало пользовательского пути |
| Must have | Создание и отправка заявки | Получение исходных данных |
| Must have | Проверка полноты данных | Исключение неполных обращений |
| Must have | Скоринговая оценка | Определение уровня риска |
| Must have | Логика кредитного решения | Основная бизнес-функция |
| Must have | Статусы заявки | Управление состоянием процесса |
| Must have | Ручное рассмотрение | Обработка нестандартных случаев |
| Must have | Сохранение данных | Непрерывность процесса |
| Should have | Автозаполнение сведений по ИНН | Удобство оформления |
| Should have | Объяснение факторов риска сотруднику | Поддержка принятия решения |
| Should have | Предложение альтернативных условий | Повышение гибкости кредитования |
| Could have | Расширенная продуктовая аналитика | Контроль эффективности |
| Could have | Дополнительная персонализация | Улучшение клиентского опыта |
| Won't have в MVP | Реальная банковская выдача | Нет доступа к банковской инфраструктуре |
| Won't have в MVP | Реальные интеграции с закрытыми системами | Используются симуляторы |
| Won't have в MVP | Полноценный электронный документооборот | Высокая сложность интеграции |


### 3.3. Основные компоненты MVP

**Клиентский интерфейс:** выбор продукта, заполнение заявки, просмотр статуса, получение решения.

**Интерфейс сотрудника:** просмотр заявок, анализ факторов риска, принятие решений по обращениям, требующим ручной проверки.

**Скоринговая модель:** оценка вероятности дефолта на основании характеристик клиента и кредита.

**Decision Engine:** применение кредитных правил и маршрутизация заявок.

**Внешние источники:** имитация получения данных ЕГРЮЛ/ЕГРИП, ФНС и БКИ.

### 3.4. Обоснование MVP

При разработке минимального продукта приоритет отдан функциям, которые позволяют связать клиентский путь с внутренней обработкой заявки.

Дополнительные сервисы и сложные интеграции намеренно вынесены за пределы MVP, поскольку они не являются обязательными для демонстрации основной бизнес-ценности.

## 4. Порог суммы для обязательной ручной проверки

### 4.1. Назначение

Порог суммы ограничивает возможность автоматического одобрения крупных кредитных заявок.

Даже если скоринговая модель показывает низкую вероятность дефолта, крупное финансирование может требовать дополнительного контроля со стороны сотрудника.

### 4.2. Установленный параметр

В конфигурации Decision Engine проекта используется следующее значение:

**MANUAL_REVIEW_AMOUNT = 3 000 000 ₽**

Заявка с суммой предложения свыше установленного порога направляется на ручное рассмотрение при отсутствии предшествующих оснований для отказа.

### 4.3. Обоснование

Необходимость порога объясняется сочетанием кредитного риска и операционной эффективности.

**Первый фактор — размер возможных потерь.** При одинаковой вероятности дефолта потенциальный денежный ущерб от крупного кредита может быть выше.

**Второй фактор — стоимость ручной обработки.** Проверка каждой заявки сотрудником увеличивает расходы и время рассмотрения.

**Третий фактор — распределение ресурсов.** Автоматизация стандартных обращений позволяет сотрудникам уделять больше внимания сложным случаям.

**Четвёртый фактор — управляемость системы.** Использование конфигурационного параметра позволяет изменять границу автоматизации.

### 4.4. Дополнительные правила кредитного решения

Реализованная логика учитывает не только сумму кредита и вероятность дефолта.

В Decision Engine также предусмотрены:

- Проверка обязательных данных.
- Проверка критических ограничений.
- Оценка долговой и платёжной нагрузки.
- Анализ дополнительных факторов риска.
- Возможность предложить меньшую сумму финансирования.
- Передача нестандартных заявок сотруднику.

Порог 3 млн ₽ применяется к рассчитанной сумме предложения после возможной корректировки из-за платёжной нагрузки.

Поэтому сама по себе запрошенная сумма более 3 млн ₽ не гарантирует ручной разбор: ранее могут сработать отказ либо корректировка суммы.

### 4.5. Ограничения принятого решения

Порог 3 млн ₽ является демонстрационным параметром кредитной политики MVP.

Для его обоснованной оптимизации на реальных данных необходимо оценивать распределение заявок по суммам, ожидаемые кредитные потери, нагрузку на сотрудников и стоимость ручной обработки.

### 4.6. Вывод

Правило обязательной ручной проверки крупных кредитных предложений позволяет ограничить автоматическое принятие решений и сохранить дополнительный контроль риска без необходимости передавать сотруднику каждую стандартную заявку.

## 5. Продуктовые метрики

### 5.1. Цель измерения

Продуктовые метрики позволяют определить, насколько кредитный кабинет повышает эффективность обработки заявок и упрощает клиентский путь.

Выделены четыре основных направления измерения:

- Автоматизация кредитных решений.
- Скорость обработки.
- Нагрузка на сотрудников.
- Удобство пользовательского пути.

### 5.2. Доля автоматических решений

**Определение:** процент рассмотренных заявок, получивших итоговое автоматическое решение.

**Формула:**

Доля автоматических решений = (Количество автоматических одобрений + количество автоматических отказов) / количество рассмотренных заявок × 100%.

**Целевой ориентир:** не менее 75%.

Показатель используется для оценки уровня автоматизации кредитного конвейера.

### 5.3. Время до решения

**Определение:** время от отправки заявки до вынесения итогового кредитного решения.

**Формула:**

Время до решения = Время итогового решения − Время подачи заявки.

**Целевой ориентир для автоматической ветки:** не более 2 минут.

Для анализа рекомендуется использовать медиану и 95-й перцентиль продолжительности обработки.

Время ручного рассмотрения и ожидания дополнительных сведений следует анализировать отдельно.

### 5.4. Доля ручного разбора

**Определение:** процент рассмотренных заявок, направленных сотруднику банка.

**Формула:**

Доля ручного разбора = Количество заявок, направленных на ручной разбор / количество рассмотренных заявок × 100%.

**Предварительный целевой диапазон:** 15–20%.

Показатель отражает нагрузку на сотрудников и зависит от правил маршрутизации, качества данных и распределения кредитного риска.

### 5.5. Отвал пользователей по шагам

**Определение:** доля пользователей, которые начали определённый шаг оформления, но не завершили его.

**Формула:**

Отвал на шаге = (Количество начавших шаг − количество завершивших шаг) / количество начавших шаг × 100%.

Необходимо учитывать возможность сохранения черновиков и возвращения к заявке позже.

### 5.6. Конверсия в отправленную заявку

**Определение:** доля начатых заявок, которые были успешно отправлены на рассмотрение.

**Формула:**

Конверсия = Количество отправленных заявок / количество начатых заявок × 100%.

**Предварительная целевая гипотеза:** не менее 75%.

### 5.7. Сводная таблица KPI

| Метрика | Целевой показатель | Назначение |
|---|---|---|
| Доля автоматических решений | ≥ 75% | Оценка автоматизации |
| Время автоматического решения | ≤ 2 минуты | Оценка скорости |
| Доля ручного разбора | 15–20% | Контроль нагрузки |
| Отвал по шагам | Снижение | Оценка удобства |
| Конверсия в отправку | ≥ 75% | Оценка завершения анкеты |

**Важно:** приведённые показатели являются целями MVP. Фактические значения должны быть рассчитаны по результатам тестирования, а не представлены как достигнутые.

### 5.8. Сбор аналитических событий

Для расчёта метрик рекомендуется фиксировать:

| Событие | Описание |
|---|---|
| application_started | Начало оформления заявки |
| step_completed | Завершение этапа анкеты |
| application_submitted | Отправка заявки |
| scoring_completed | Завершение скоринга |
| manual_review_started | Начало ручного разбора |
| additional_info_requested | Запрос дополнительных сведений |
| decision_made | Вынесение итогового решения |

Для каждого события рекомендуется сохранять идентификатор заявки, название события и время возникновения.

Необходимо отдельно различать факт наличия событий в проектной модели и фактическую реализацию аналитического трекинга.

### 5.9. Ожидаемый эффект

**Для клиента:** более быстрое получение решения по стандартным заявкам, меньше повторных действий и прозрачное отслеживание статуса.

**Для банка:** сокращение рутинной нагрузки, повышение управляемости кредитного процесса и возможность анализа узких мест.

После запуска MVP эффективность должна подтверждаться фактическими измерениями.

## 6. Итоговые выводы

Проведённая продуктовая аналитика позволяет сформулировать основные направления развития кредитного кабинета.

Выявлены пять ключевых гипотез о проблемах пользователей, определены основные задачи предпринимателя и разработана модель улучшенного клиентского пути.

Приоритизация по MoSCoW позволила выделить функциональность, необходимую для демонстрации сквозного кредитного процесса.

Обоснован механизм обязательной ручной проверки крупных кредитных предложений с использованием конфигурируемого порога 3 млн рублей.

Определены основные продуктовые метрики и методика измерения ожидаемого эффекта.

Главный вывод заключается в том, что ценность проекта определяется не только наличием скоринговой модели, но и качеством всего процесса: от понятного оформления заявки до прозрачного, управляемого и своевременного кредитного решения.
